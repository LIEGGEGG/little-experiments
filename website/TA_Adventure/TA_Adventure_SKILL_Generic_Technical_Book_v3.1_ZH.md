# Source-First Interactive Book Adventure — 通用 Skill v3.1（中文版）

## 0. 目的

将**任何权威的技术/工具类手册**转换为互动学习产品，帮助读者真正读完、理解、核验、检索并复用其中的内容，同时避免 AI 在无提示的情况下擅自发明课程体系或覆盖原书本身。

核心规则：

> **先有 SOURCE → 再做 EXPLANATION → 最后才 REORGANIZATION。**

由原始资料决定“有哪些知识”。只有在相关原文已经完成提取之后，AI 才可以进行解释、比较、重组、提问、生成练习，以及构建检索结构。

本 Skill 适用于软件手册、引擎/工具书、生产流程手册、API 指南、技术美术书籍、DCC 手册、工程实践手册，以及其他结构化参考资料。

---

# 1. 来源层级模型（Provenance model）

所有面向读者的内容都必须明确属于以下某一层：

- `SOURCE` — 由提供的原书/手册直接支持的内容。
- `DERIVED` — 基于 SOURCE 生成的 AI 解释、类比、心智模型、苏格拉底式问题、小测试或练习。
- `EXTERNAL` — 当前厂商文档、后续版本、会议分享、案例研究或其他外部资料。
- `USER_NOTE` — 读者自己的经验、笔记、异议、项目案例。

绝不能把这些层级混在一个没有标识的段落中。

对于具有明显版本时效性的书籍，应原样保留书中的历史性结论。如果后续版本已经不同，原书陈述继续保留在 `SOURCE`，更新内容另行作为 `EXTERNAL_UPDATE` 添加。

---

# 2. 先证据，后内容

任何声称“来自原书”的结论，在进入产品之前都必须先有证据。

最小 Claim 记录：

```js
{
  documentId: "stable-source-id",
  page: 42,
  section: "Exact source heading",
  claim: "Concise supported statement",
  evidence: "Short exact excerpt or precise source span",
  evidenceType: "text" // text | figure | table | caption
}
```

禁止流程：

```text
AI 先写课程 → 再搜索大致相似的文字 → 最后补一个引用
```

正确流程：

```text
原书页面 → 证据 → Source Unit → 教学转化 → 人工审核 → 公开检索视图
```

如果原书无法支持某个结论，就应删除它，或者明确放入独立的外部资料/推理层中。

---

# 3. 原书检查与 Canonical 层级

在生成课程内容之前：

1. 确认书名、版本、出版方、出版年份、总页数；
2. 检查完整目录；
3. 记录准确的顶层章节结构和子标题；
4. 识别附录、资源页、术语表、版本说明、尾页等特殊区域；
5. 检查图片/表格是否承载了纯文本解析无法恢复的信息；
6. 盘点原书明确提供的推荐阅读链接与学习资源。

正常阅读视图遵循作者原本的顺序。除非用户明确要求额外生成一套“派生课程”，否则不要把原书擅自重构成初级 / 中级 / 高级 / 大师之类的人造学习路径。

如果出于产品组织需要，一个 Source Unit 跨越了两个原书标题，需要把它记录为明确的映射例外；不能假装原书本身的层级发生了变化。

---

# 4. 全书扩展前，先做最小可验证结构（MVS）

先选连续的少量内容，通常为 1–3 个原书小节：

```text
SOURCE PASSAGE
→ SOURCE UNIT
→ DERIVED EXPLANATION
→ ANALOGY / MENTAL MODEL
→ SOCRATIC QUESTION + HINT + REFERENCE ANSWER
→ SOURCE-BOUND QUIZ
→ PRACTICE
→ HUMAN REVIEW
```

在审核者确认以下内容可接受之前，不要一次扩展整本书：原文提取、解释质量、测试题质量、术语策略、审核流程。

MVS 通过以后，应恢复完整的产品体验，而不是让网站长期停留在一个纯验证工具的形态。

---

# 5. Source Unit 数据结构

一个 Source Unit 应代表一个完整、由原书支持的概念或工作流，而不是机械地平均切页。

推荐结构：

```js
{
  id: "stable_unit_id",
  chapterId: "source_chapter_id",
  title: "reader-facing title",
  pages: "P12–13",
  xp: 60,

  sourceSummary: "Chinese-first or reader-language summary",
  claims: [
    { claim: "...", evidence: "...", page: 12 }
  ],

  scenario: "source-grounded working situation",
  analogy: "plain-language analogy",
  mental: ["step 1", "step 2", "step 3"],
  socratic: "question",
  hint: "hint + explicit reference answer",

  tags: ["Canonical Tool", "Canonical Concept"],
  quiz: { q: "...", opts: ["..."], correct: 2, why: "..." },
  quest: ["observable task 1", "observable task 2"],

  figures: [],
  deeperReading: []
}
```

稳定 ID 应在内容修订后继续保持不变，以保证阅读进度与 Review JSON 的兼容性。

---

# 6. 读者语言策略

对于中文读者版本：

- 解释与原书内容总结以中文为主；
- 实际工作中通常直接使用英文的官方名称/专业术语，应保留英文；
- 当中文有助于理解时，优先使用 `中文（Canonical English）`；
- 用于核验的原文 Evidence 保留原始语言；
- 不要仅仅为了让界面看起来“双语”，就强行翻译一个本来工作中不会翻译的术语。

审核后台中，AI 整理后的总结要明确标注为派生内容，例如 `原书内容总结（AI整理）`，不能让人误以为它就是原文引用。

# 7. 学习转化

## 7.1 场景案例（Scenario）
使用一个可信、具体的工作场景，让原书概念变得可理解。不要补充原书并未建立的事实性要求。

## 7.2 类比（Analogy）
类比应该解释机制，而不是只起装饰作用。好的类比应该能帮助读者预测系统行为。如果类比制造了错误的一一对应关系，就需要重写。

## 7.3 FROM ZERO 心智模型
优先用 2–4 个因果步骤：

```text
现在存在什么问题？
→ 哪些数据 / 对象 / 流程发生变化？
→ 哪个工具 / 系统在中间发挥作用？
→ 读者最终需要做出什么判断？
```

## 7.4 苏格拉底式问题、提示与答案
提示应该支持主动回忆，但最终必须能够解决问题。

要求的 UX：

```text
问题
→ 隐藏提示：指向原书线索
→ 明确参考答案：直接回答问题
```

不要让读者点击“查看提示”以后，只得到另一个模糊问题。

## 7.5 小测试（Quiz）
小测试的正确答案必须能被原书支持。

整本书层面的反模式检查：

- 正确答案不能系统性地总是最长选项；
- 正确答案位置不能大量集中在某一个固定索引；
- 干扰项应该是对同一概念的合理误解，而不是一眼就能排除的荒谬选项；
- 选项长度应大致平衡，但不要刻意做得完全一样而显得不自然；
- 答题后的解释应说明为什么正确选项能由原书推出。

## 7.6 实践 / Quest
任务应产生可观察的结果，例如：

- 一份比较；
- 一个配置以及观察到的结果；
- 一张图；
- 一个带判断标准的决策；
- 一个小型产物；
- 对真实工具/项目的一次检查。

应避免类似“写下你觉得可能会出什么问题”这种空泛任务，除非这份文字本身确实能在后续工作中产生价值。

---

# 8. 术语与 Tag 架构

Tag 用于检索和图谱结构，不用于构建宽泛的激励型分类体系。

多数 Source Unit 使用 1–4 个术语即可。优先选择官方产品名、API、文件格式、系统名称以及 canonical 技术概念。

将“身份”和“显示方式”分开：

```js
TERMS = {
  "Canonical Term": {
    alias: "optional localized name",
    mode: "canonical", // canonical | bilingual | localized
    search: ["approved synonym", "common abbreviation"]
  }
}
```

不能仅仅因为中文译名发生变化，就修改 canonical key。

Private Review Build 必须提供仅后台可见的术语审核接口，至少包含：

- canonical term；
- 可编辑的本地化别名；
- 显示模式；
- 搜索别名；
- 状态；
- 审核备注。

搜索应同时匹配 canonical term、已审核的中文别名与认可的同义词。

---

# 9. 配图与视觉证据

当图片本身承载信息时，它就是原书证据的一部分。

选择层级：

1. `core` — 理解该单元必须依赖的图表/截图；
2. `supporting` — 有助于理解 UI 或上下文的辅助图；
3. `original page` — 原始页面始终作为最终上下文参考。

对于 PDF，优先直接提取其内嵌原始图片流。不要仅为了缩小单文件 HTML，就再次缩放或重新编码原始 JPEG。如果原图本身分辨率较低，应限制合理的最大显示尺寸，而不是用 AI 放大或补造不存在的细节。

每张入选图片都应保存页码、原书图注以及它在当前单元中的作用。图注必须描述“实际提取到的图片”，而不是泛泛描述所在页面的主题。

Public Build 与 Review Build 使用完全相同的原书图片资产。

---

# 10. 推荐阅读与外部扩展

原书明确推荐的资源属于 Source Metadata，而不是装饰内容。

推荐的 `GO DEEPER` 分层：

1. `BOOK / 原书推荐` — 原书明确推荐的全部链接；
2. `CURRENT / 当前官方文档` — 另外核验的当前厂商官方文档；
3. `PRACTICE / 权威实战` — 权威生产实践分享 / 案例，例如 GDC、SIGGRAPH、厂商工程分享、工作室复盘。

发布之前：

- 审核每一个 `More resources` 区块；
- 保留 e-book 卡片、推荐学习路径，以及明确的 “read / watch / learn more / check out” 资源；
- 每条 BOOK 资源都记录其原书页码；
- 只在同一 Unit 内对完全相同的 URL 去重；
- 绝不能静默地用当前链接替换原书的历史链接；
- QA 必须做到：原书明确推荐资源缺失数为 0。

任何 External 扩展资料都不能作为 SOURCE Claim 的证据。

---

# 11. Private Review Build

Review 属于作者工作流，不属于读者体验。

每个 Unit 的状态：

```text
PENDING
APPROVED
REQUEST_REVISION
```

一个 Unit 可以同时存在多个独立修改问题：

```js
{
  unitId: "unit_17",
  status: "REQUEST_REVISION",
  issues: [
    { area: "Analogy", feedback: "Mechanism is unclear." },
    { area: "Quest", feedback: "Task has no observable outcome." }
  ]
}
```

审核者看到的问题分类应本地化为读者语言；为了兼容性，内部稳定 key 可以继续使用英文。

建议的问题分类：

```text
原书事实 / 引用准确性
原书内容总结（AI整理）
场景案例
类比
心智模型
思考题 / 提示
小测试
动手任务
专业术语 / Tag
原书配图 / 推荐阅读
```

审核者只需要指出问题，不需要替 AI 重写内容。

修改契约：

```text
导出反馈
→ AI 重新打开准确的原书页面
→ 只修改被标记的字段 / Unit
→ 除非确实存在全局规则变更，否则已通过内容逐字保留
→ 重新导入 / 继续审核
```

审核状态必须支持导出/导入，不能只依赖 localStorage。

---

# 12. Public Build 隔离

必须生成物理上独立的两个产物：

```text
PRIVATE REVIEW BUILD
- Evidence + 派生学习内容
- 审核状态
- 多问题反馈
- 术语审核
- 导入 / 导出

PUBLIC READER BUILD
- 以原书为依据的学习内容
- 原书配图与页码
- Map / Graph / Search
- Quiz / Practice / Progress
- 不包含 Review 面板
- 不包含 Review 状态
- 不包含审核者反馈
- 不包含术语审核状态 / 数据
- 不包含休眠状态的 Review 导出函数
```

不能只通过 CSS 隐藏私有 UI。

面向读者的文案只描述“当前产品是什么”。不要谈原型历史，也不要解释页面“不是某某东西”。

---

# 13. 全书层级

当书的内容规模增大时，应增加层级，而不是不断缩小一切。

```text
READ  → BOOK → CHAPTER → SOURCE UNIT
MAP   → BOOK MAP → CHAPTER MAP
GRAPH → CORE TERM NETWORK → FOCUS/HIGHLIGHT → SEARCH ALL TERMS
```

心智模型：

- `READ = 学习`
- `MAP = 定位 / 进度`
- `GRAPH = 连接 / 再次遇见`

## READ
默认只展开当前章节。其他章节收起为紧凑的进度行。可以提供“全书目录抽屉”用于远距离跳转。

## MAP
一级显示原书章节 / 区域。二级显示该章节内按原书顺序排列的 Source Unit。地图连线表达的是作者的阅读顺序，而不是语义相似度。阅读进度动画主要属于这里。

## GRAPH
图谱节点使用 canonical 专业术语，而不是 Lesson / Unit 节点。边来自可解释的共现关系或原书明确关系。

当用户选择一个术语时，整张核心网络必须继续保留。选择只是 Focus 状态：

- 保留核心网络；
- 降低无关节点 / 边的亮度；
- 高亮直接关系；
- 如果产品使用双向动画连线，则继续保留；
- 点击图谱空白处清除 Focus；
- 提供明确可见的“清除高亮”控件；
- 搜索可以临时显示一个非核心术语，但不能因此删除核心网络。

不要在图谱下方重复渲染整墙的完整卡片 / Index。选中术语的上下文可以只展示：首次出现、原书页码、直接关联术语，以及返回对应 Source Unit 的入口。

---

# 14. 搜索与导航契约

所有跳转到 Source Unit 的入口必须走同一个 canonical 导航函数。该函数至少需要：

1. 校验 Unit ID；
2. 更新当前 Unit；
3. 展开正确章节；
4. 切换到 Reading；
5. 重新渲染必要视图 / HUD；
6. 关闭临时浮层；
7. 按 sticky header 偏移量滚动到正确阅读起点。

全局搜索、地图节点、图谱术语结果、Related Units、上一节 / 下一节、完成动作、Private Review 列表，都应通过同一条 Unit 导航路径解析。

---

# 15. 移动端与响应式行为

不能只是把桌面页面缩小。

窄屏下：

- 折叠章节导航；
- 长文阅读保持单栏；
- 原书配图占满可用宽度，图注放在下方；
- 心智模型、延伸阅读、Quiz、Quest 清晰堆叠；
- 使用适合触控的按钮；
- 如果 Canvas 无法完整放下，优先只保留**单轴横向拖动**，页面本身负责纵向滚动；
- 避免嵌套的双轴滚动区域；
- 单击选择图谱节点，进入正文要有明确按钮 / 链接；
- 中英文长标题与术语 Chip 必须安全换行。

桌面端中，章节 Map 如果只有少量 Unit，应尽量完整显示，不使用滚动条。

# 16. 产品个性、视觉系统与动画语言

Source-first 架构不意味着界面必须无趣。这个学习产品应当像一个紧凑的“游戏 + 工具”混合体：足够有趣，让人愿意继续探索；同时足够克制，让原书始终保持权威地位。

除非未来项目明确要求另一套美术方向，否则默认以当前 **TA Adventure 视觉外壳**作为参考实现。换成其他工具书时，可以调整品牌色，但应尽量保留这里定义的语义角色、层级关系与动画语言，除非审核者明确要求改变。

## 16.1 视觉核心

默认视觉由以下元素组成：

- 深色技术工作台；
- Pixel / RPG 式框架；
- 高饱和、带明确语义的功能色；
- 黑色硬边框与错位硬阴影；
- 很轻的 CRT / 扫描线质感；
- 克制的像素网格背景；
- 桌面端信息密度较高，但卡片之间留有明确呼吸空间；
- 阅读进度与导航具有游戏反馈；
- 最终 Epilogue 刻意切换成更柔和、更电影化的视觉语言。

界面应当有“手工做出来的游戏工具感”，**不要**做成通用 SaaS 后台，也**不要**把原 PDF 直接复刻成网页。

## 16.2 标准配色

默认 CSS Token：

```css
:root {
  --bg:      #0A0A0A;
  --panel:   #1A1A2E;
  --panel2:  #16213E;
  --gold:    #FFD700;
  --gold2:   #FFEA3A;
  --red:     #FF2079;
  --green:   #00FF41;
  --cyan:    #00B4FF;
  --purple:  #9D00FF;
  --orange:  #FF8C00;
  --magenta: #FF00FF;
  --cream:   #F5E6D3;
  --muted:   #AAB0BC;
  --shadow:  4px 4px 0 #000;
  --shadow-lg: 6px 6px 0 #000;
}
```

语义约定：

- **金黄 / 黄色**：XP、完成度、主进度、当前路线、主要行动按钮、滚动条滑块。
- **青色**：导航 / 当前学习上下文、场景案例、FROM ZERO、Tag、世界地图强调。
- **橙色**：SOURCE / Evidence / Review 来源层。
- **洋红**：类比与生活化解释。
- **紫色**：思考题 / Socratic / 更深层概念关联。
- **绿色**：Quest、完成、成功状态。
- **白色**：原书配图与中性证据展示。
- **红 / 粉**：警告、错误答案、失败或异常状态。

不要把高饱和色当作随机装饰。一个颜色重复出现时，应尽量重复表达同一种意义。

## 16.3 字体体系

默认层级：

- 中文长文：`Microsoft YaHei`、`PingFang SC` 或同级可读无衬线字体；
- Pixel 展示文字：`Press Start 2P`，中文使用无衬线 fallback；
- 次级复古 metadata 可使用 `VT323` / `Silkscreen`；
- Epilogue 可以刻意切换到 `Noto Serif SC`、`Songti SC` 等衬线字体。

规则：

- 正文可读性高于“像素纯度”；
- Pixel 字体只用于 HUD、标签、Badge、Tab、计数器和短标题；
- 中文长标题应改用清晰的粗体无衬线，而不是为了坚持 Pixel 字体被迫缩得很小；
- 中英文混排必须安全换行，可使用 `overflow-wrap:anywhere` 或等效规则。

## 16.4 全局表面质感

默认页面背景：

- 接近纯黑；
- 极轻的 2px 像素 / 网格纹理；
- 固定的低透明度横向扫描线；
- CRT 效果绝不能以牺牲文字对比度为代价。

卡片和面板：

```text
3px 硬边框
+ 4–6px 错位黑色或功能色阴影
+ 方形 / 极小圆角
+ 跨在上边框上的标签牌
```

主体阅读界面不要使用柔和 Glassmorphism。唯一允许明显脱离的是 Epilogue，因为那里本来就需要视觉断点。

滚动条：

- 深色轨道；
- 黄色 / 金色滑块；
- Hover 时变成更亮的黄色；
- 能去掉的内部滚动条就去掉，不要依赖层层嵌套的滚动区。

## 16.5 桌面端布局

参考最大内容宽度：约 **1220px**。

READ 页面：

```text
Sticky HUD
→ 顶部 View Tabs
→ 双栏阅读
   ├─ 章节 / Unit 导航 ≈ 400px
   └─ 当前 Source Unit 占据剩余宽度
```

章节导航可以 Sticky，但不能抢过正文的视觉权重。

单元阅读节奏：

```text
Hero / 标题
→ 场景案例
→ SOURCE / Evidence
→ 有价值时加入原书配图
→ 类比
→ FROM ZERO 心智模型
→ 思考题 / Socratic
→ 延伸阅读
→ Tags / Related
→ Quiz
→ Quest
→ 上一节 / 完成 / 下一节
```

语义卡片之间保持明确的纵向间距。遇到内容密度问题，不要靠不断缩字体“硬塞进去”。

## 16.6 内容区颜色语言

默认映射：

```text
场景案例            → 青色
SOURCE / Evidence   → 橙色，可使用虚线边框
原书配图            → 白色 / 中性
日常类比            → 洋红
FROM ZERO           → 青色
思考题 / Socratic   → 紫色
延伸阅读            → 紫色
Tags / Related      → 青色
Quiz                → 金黄 / 黄色
Quest               → 绿色
Private Review      → 橙色
```

区块标签跨在卡片上边框上，像游戏 UI 的小标题牌。Label 尽量短；面向用户的操作按钮优先使用用户语言。

## 16.7 HUD、Tab、搜索与进度

HUD 特征：

- 深色块状面板；
- 黑色硬边框 + 错位阴影；
- 方形黄色 Logo Tile；
- 黄色产品名；
- 使用重复条纹 / 分段感的黄色 XP Bar；
- 紧凑的阅读进度计数；
- 全局搜索使用青色描边，搜索结果也沿用青色语义。

XP 变化优先使用离散 / Step 动画，而不是液体式平滑滑动。全书完成时必须视觉上真正达到 100%。

顶层 Tabs 使用游戏菜单式处理：

- 未选中为深色；
- 当前 Tab 为黄色；
- Private Review 可以保留橙色；
- 手机端允许横向滑动，桌面端不应默认依赖横向滚动。

## 16.8 世界地图视觉语言

MAP 回答的是：**“我在这本书的哪里？”**

桌面端：

- 一级章节地图应尽量完整放进可视区域，不依赖内部滚动；
- 进入章节后，再显示该章节内部 Unit 路线；
- 章节 Unit 数量不多时，优先一条清楚的路线，而不是做成稠密网络；
- 已完成 / 当前 / 未读状态必须直观区分。

动画：

- 黄色 / 金色旅行标记沿已完成与当前路径移动；
- 当前节点可以轻微闪烁 / 呼吸；
- 已完成节点可以有紧凑的 `[OK]` 状态；
- 背景像素 / 星点可以低强度闪烁；
- 动画要强化“旅行 / 前进”，不能变成屏保。

MAP 不要复用 GRAPH 的关系语义。它表达的是作者原书的阅读地理与进度。

## 16.9 知识图谱视觉语言

GRAPH 回答的是：**“这些 canonical 专业术语之间如何关联？”**

核心行为：

- 核心大图始终保留；
- 选择某个术语后，高亮该节点与直接关联；
- 无关节点降低透明度，但不消失；
- 点击画布空白或明确的“清除高亮”按钮可以恢复总图；
- 搜索到非核心长尾术语时，可以临时把它加入图中，但不能用局部图替换整个核心网络。

关系动画：

- 高亮关系时使用**两条平行关系线**；
- 两条线上各有小型黄色 / 金色像素块，沿相反方向移动；
- 这种“反向对流的双链动画”是当前产品的重要标志，应在重构 Graph 时保留；
- 当前节点 = 最强高亮；
- 一跳直接邻居 = 高可见度；
- 无关节点 = 降低透明度；
- 文字必须可读，不能把节点文字互相压住当作一种风格。

图谱空闲时也可以有轻微生命感，但最明显的动画应由用户选择节点之后触发。

## 16.10 动画语言

主体产品的动画应当是：**离散、短、功能明确、带 Pixel 感。**

推荐：

- XP、开始界面网格、Blink、Pixel UI 变化使用 `steps()`；
- Button Press / Wrong Answer / Navigation Flash 通常控制在 50–300ms；
- 轻微 Blink / Pulse 循环约 0.8–1.5s；
- 只有世界地图旅行、图谱关系流动、背景环境可以持续慢速播放；
- 避免弹簧感很强的 Bounce、过度 Parallax、大幅自动镜头移动。

标志性微动画：

- 保存 / 完成：绿色 Flash；
- Quiz 错误：极小横向 Shake + 红 / 粉反馈；
- Quiz 正确：绿色 Pulse；
- 导航到新位置：短暂黄色 Flash；
- Think Label：克制的 Step Blink；
- Map Route：黄色旅行像素块；
- Graph Relation：双链上的黄色像素反向流动。

必须支持 `prefers-reduced-motion`。Reduced Motion 下应去掉循环与过渡动画，但不能隐藏任何信息。

## 16.11 欢迎 / 游戏开始界面

首次进入的 Start Screen 是产品的一部分，不是普通 Splash Page。

默认处理：

- 近黑背景；
- 大间距黄色网格，以 Step 方式缓慢移动；
- 轻微 Scanline；
- 居中的深色卡片，4px 硬边框 + 更大的黄色错位阴影；
- 四角 Pixel 装饰块；
- 黄色 Pixel 标题；
- 简单 Float / Pulse 的游戏图标或角色；
- 新读者显示 `开始学习`，有历史进度时显示 `继续学习`；
- 可显示已完成 Unit 数和下一个 Unit。

用户点击后应快速离开 Start Screen；内部页面跳转不能反复播放它。

## 16.12 完结与 Epilogue

主体阅读使用 Pixel / RPG 外壳。**全书最后的 Epilogue 刻意允许脱离这一套视觉。**

当前参考方向：

- 全屏夜空 / 黄昏渐变；
- 地平线有柔和的暖色光；
- 星点 / 粒子逐步汇聚成象征性的路径、桥或其他形状；
- 一个很小的发光“旅人”沿完成后的形状移动；
- 半透明中央内容容器；
- 中文衬线字体；
- 暖奶油 / 金色，而不是主体界面的霓虹高饱和色；
- 使用缓慢、平滑、电影化的运动，而不是 `steps()` Pixel 动画；
- Public Build 可以使用“第一次随机、之后固定”的多结局池。

这个视觉断点要让读者感受到：**学习 UI 已经结束，现在是奖励 / 告别。**

全书结尾不能继续复用普通 `UNIT CLEARED` 的动画。

## 16.13 移动端视觉与动画适配

不能只是把桌面页面缩小。

- 长文阅读变成单栏；
- 章节导航折叠为明确的 Drawer / Button；
- 语义卡片占满可用宽度并保持可读；
- Label 自动换行，不允许重叠；
- 触控目标保持足够大；
- Map / Graph 允许**仅横向拖动**，纵向滚动交给页面本身；
- 不允许 Canvas 内部同时上下左右双轴滚动；
- Graph 单击即选中，进入正文使用独立明确操作；
- 移动端 Start Screen 应压缩纵向空间，而不是把字体缩到不可读；
- 移动端 Epilogue 作为全屏纵向阅读构图，操作按钮纵向堆叠。

## 16.14 视觉 QA Gate

发布前至少检查：

- 1280 / 1440 / 1920 左右桌面宽度；
- 360–430px 手机宽度；
- 很长的中文标题；
- 很长的英文 canonical term；
- Unit 的当前 / 已完成 / 未读状态；
- 世界地图一级 / 二级；
- 图谱空闲 / 选中 / 搜索 / 清除高亮状态；
- 原书配图与图注；
- Quiz 错误 / 正确反馈；
- 0% / 中间进度 / 100% XP；
- 首次欢迎页与有历史进度时的欢迎页；
- Epilogue 与 Replay；
- `prefers-reduced-motion`。

出现文字重叠、节点 Label 被裁切、Canvas 双轴嵌套滚动、关键操作不可见、功能色语义不一致，均视为发布阻断问题。

# 17. 进度与完结

Progress 表示“阅读完成度”，不是职业能力等级。

要求：

- XP 来源于已完成的 Source Unit；
- 100% 完成时，XP 条必须视觉上真正达到 100%；
- 最后一个 Unit 完成后，应触发独立的完结 / Epilogue 状态，而不是普通的 “Unit Clear” 弹窗；
- Epilogue 可以重复查看；
- 为了让结尾更难忘，Epilogue 可以脱离主体产品的视觉规范；
- 不要仅因为读完整本书，就宣称读者已经成为大师 / 专家。

## 可选：公开版多结局奖励

公开网站可以让不同读者获得不同结局。

推荐实现：

- 准备一组经过审核的 Epilogue；
- 第一次完成全书时随机分配一个；
- 把该结局保存在本地，使再次查看时保持一致；
- 可以包含稀有结局；
- **不要**根据行为推断人格、技能、健康、身份或其他敏感特征；
- 不要假装随机结局是根据用户私人数据单独生成的；
- 如果没有账号 / 后端，不同设备或浏览器可能获得不同结局。

这样可以制造“像是专属于自己的奖励”，同时不需要对读者做画像。

# 18. 部署

审核阶段，单文件 HTML 很方便。扩展到整本书后，静态网站通常更合适：

```text
/index.html
/app.js
/data/*.json
/assets/figures/*
```

GitHub Pages 适合部署静态 Public Build。通过 `https` 在标准浏览器环境打开，可以避免手机文件预览 App 直接打开大型 JS HTML 时的很多限制。

除非增加单独的同步后端，否则 localStorage 中的阅读进度只属于当前设备 / 浏览器。

# 19. QA Gate

发布之前验证：

## Source
- 每一条事实性 SOURCE Claim 都有页码 / Evidence；
- 不存在“先写结论后补引用”；
- 原书章节顺序与真实 TOC 一致；
- 历史版本陈述继续保留历史语境；
- 选中的配图与图注一一对应；
- 原书明确推荐的所有链接都已被盘点。

## Learning
- 派生总结保持原意；
- Hint 包含参考答案；
- 类比在解释机制，而不是歪曲机制；
- Quiz 不能通过答案长度 / 固定位置模式猜出；
- Practice 任务具有可观察的实际价值。

## Terminology
- canonical 身份保持稳定；
- 本地化别名经过审核；
- 搜索别名不会改变图谱身份；
- 长尾术语不会把默认核心图谱撑爆。

## Product
- READ / MAP / GRAPH 职责清晰区分；
- Focus 状态下核心图谱仍然存在；
- 图谱下方没有重复的 Index / 卡片墙；
- 所有跳转路径正常；
- 移动端没有意外的嵌套双轴滚动。

## Review / Public 隔离
- Public 不含 Review DOM / State / Feedback / Export Logic；
- Private Review 支持单 Unit 多问题以及术语审核；
- Review JSON 可以正确导出再导回。

## Completion
- 全书完成时进度真正填满；
- 结局可重复查看；
- 如果启用公开多结局，每个浏览器的分配应保持稳定，并且不使用敏感画像。

# 20. 最终理念

这个产品应该让读者更愿意回到原书，而不是更少去看原书。

> 线性阅读，非线性重遇。证据始终近到足以让你随时确认自己为什么相信它。

网站只是叠加在书上的学习界面；原书始终是最终 Evidence Layer。
